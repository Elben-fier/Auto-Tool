# 短剧审核 9.1 判定机制详解（相似度矩阵版 · 内部版本 9.4.4）

> 本文把 `短剧审核-批量判错/短剧审核9.1.user.js`（源头副本：`脚本编译/短剧/短剧审核9.1.user.txt`）**逐层拆开**：
> 页面数据怎么读 → 判定优先级怎么走 → 展开核对用什么判据 → 两种模式各自做什么动作 → 等待/重试/跳过如何兜底 → 面板与日志字段含义 → 最后列出**已知疑点**，供下一步提需求时取舍。

## 二、页面数据模型（脚本读哪些列）

### 母行（合集行）`tr.ant-table-row.ant-table-row-level-0`

> ⚠️ **取母本行必须用 `getParentRows()`（9.4.2）**：母本行和子样本行的 class **完全相同**（antd 的 level 是"表内层级"，子表自己也是 level-0）。直接全文档查会把**展开区里的子样本行**当成母本行 —— 表现为"第5列原文是「预览」、短剧名是纯数字 592、一行一行慢慢跳"。`getParentRows()` 会排掉 ① 落在 `tr.ant-table-expanded-row` 里的行、② 嵌在另一个表格里的行。

| 列 | 选择器 | 用途 |
|---|---|---|
| 第2列 | `td:nth-child(2)` | 合集 id（**唯一标识**：判完成、去重、跳过都用它） |
| 第3列 | `td:nth-child(3)` | 短剧名 → 关键词双列比对 / 相似度 |
| 第4列 | `td:nth-child(4)` | 疑似抄袭的原短剧名 → 双列比对 |
| 第5列 | `td:nth-child(5)` | **母本最高分**（＝子样本单条分的最大值）→ **母本最低线**（<90 直接全错）+ 日志标签 |
| 第7列 | `td:nth-child(7)` | 审核状态（含「已审核」→ 跳过该行） |
| 第10列 | `td:nth-child(10)` | 集数 → 慢处理判定（>300 用更长等待） |
| — | `.ant-table-row-expand-icon` | 展开 / 收起合集 |

> 单元格文本读取：`textContent` 去空白；分数用 `parseFloat`，读不到返回 `null`（**不是 0**）。

### 展开行 `tr.ant-table-expanded-row` → 子表格 `.ant-pro-table`

| 列 | 选择器 | 用途 |
|---|---|---|
| 第1列 | `td:first-child input.ant-checkbox-input` | 逐行勾选；表头全选 `thead th:first-child input.ant-checkbox-input` |
| 第2列 | `td:nth-child(2)` | 子样本 id（**上报日志取第一条的 id**，不用母本 id） |
| 第3列 | `td:nth-child(3)` | 状态码：`0`=未判定 / `594`=判错完成 / `777`·`601`=前人已判定（参与计数） |
| 第8列 | `td:nth-child(8)` | **单条分**（每条数据自己的匹配分）→ =0/读不到剔除、低分 **<80**、高分 **≥93** |

状态码解析：取单元格文本里的**第一段数字**（`toFixed` 无关），空值视为未判定。
子样本行选择器：`.ant-pro-table tbody tr.ant-table-row`（在展开行范围内查）。

## 三、主循环：选行 → 保护 → 判定 → 收尾

```
runLoop()
 ├─ pickTarget()            从「起始行」往下扫，找第一个可审行
 ├─ 匹配分读不到保护         重读 N 次 → 仍读不到则本轮跳过该合集（9.2.1，不再中断整轮）
 ├─ processOneCollection()  单合集判定 + 执行动作
 ├─ reportJudge()           上报判定日志（可选，失败不影响流程）
 ├─ ok → doneIds.add(id) / problem → 收起并永久跳过（=异常数据）
 └─ 扫不到可审行 → confirmReviewFinished()：点「查询」刷新确认两次 → 仍没有才判定审核结束
```

**pickTarget 规则（v9.2.0 起：每轮从顶往下扫 + 已审核为边界）**

1. 扫描起点 = 面板「起始行号」（`CONFIG.startRow`，默认第 1 行），**每一轮都从这里重新往下扫**，不再沿用上一轮的下标（列表刷新后会重排/补位）；
2. 「已审核」行只作**边界标记**（说明下面都已审过），本身不再当可审行；
3. 跳过：`skipIds`（=**异常数据**，本轮永久跳过）、`doneIds`（本轮已处理过）、状态含「已审核」的行；
4. 第2列 id 读不到的行走**不算候选**（视为"还没刷新好"），跳过它继续往下看 —— 只有**整段所有行**都读不到 id 才判为页面改版并立即停止；
5. 第一个可审行就是本轮目标；一个都没有 → 交给 `confirmReviewFinished()` 做结束确认：
   - 点页面「查询」刷新列表 → 等加载完成 + `endConfirmSettleMs`(1.5s) 稳定 → 重扫；
   - 默认**点两次**（`endConfirmRounds`=2）；任何一次刷新后出现可审行 → 继续审；
   - 两次都扫不到可审行 → 判定**审核结束**，弹窗汇总。
6. **"审完"的口径** = 页面除了「已审核」与「已跳过的异常数据」之外，没有未审核行。

> 说明：以前是"从 `workIndex` 往下续扫，扫到底再回绕到前面找一遍"。新做法每轮都从顶扫，**回绕由"从顶扫描"天然覆盖**，同时避免了续扫游标在列表重排后指错位置。

**「匹配分读不到」的处理（v9.2.1：重读 → 跳过 → 刷新后重试）**

9.2.0 及以前是"**相邻 N 行（`noScoreStopCount`=3）读不到第5列 → 立即停止运行并弹窗**"（当年防的是"读不到 → 直接全错"整批误判）。
9.1.7 取消"读不到 → 全错"后，这条保险已无必要用"中断整轮"实现，而实测中它**经常在列表/母本刷新途中误触发**。现在改为三段式：

1. **重读**：先等加载完成，再重读 `scoreRetryCount` 次（间隔 `scoreRetryGapMs`=1.2s）→ 读到了就用新分数继续正常判定；
2. **跳过**：仍读不到 → 记入 `notReadyIds`（=「母本还没刷新好」），**本轮先跳过该合集、继续审别的行**（不判错、不展开、不中断整轮）；点过「查询」刷新列表后自动清零重试；
3. **汇总**：同一合集跳过 `scoreGiveUpRounds`（默认 3）次仍读不到 → 进 `giveUpIds`，本轮彻底放弃（避免"跳过 → 结束确认点查询 → 又扫到 → 又跳过"来回打转），结束时在弹窗里连同 id/短剧名/行号/**第5列原文**/尝试次数一起列出，供人工处理。

安全网：`notReadyList` 累计到 `scoreSkipWarnCount`（默认 5）时，日志提示检查 `SELECTORS.parentScoreCell` —— **只提示，不停止运行**。

> 与"第2列 id 读不到"（第三节第4条）口径一致：**个别行读不到 → 跳过继续；只有整段全部读不到 → 才判页面改版并停止**。

## 四、判定链（按优先级，命中即停）

代码位置：`processOneCollection()` 第1步。顺序**不可调换**：

### ① 关键词双列比对 → 可能模式2（v9.4.0：已取消"终极关键词"）

原「终极关键词」（`ultimateKeywords` 12 个词，命中即**无条件**全错）**已在 9.4.0 整表删除**：
- 其中 11 个词本就在普通关键词表里（红果/动画/免费/剪辑/花絮/拍摄/动漫/定档/首播/画；「充电专属」由「充电」「专属」覆盖）；
- **唯一不在表里的「论剑大会」已补进 `nameKeywords`**（现 26 个词）；
- 9.1.6 为「画」做的"单字→双列比对"修法，现在**就是全部关键词的统一规则**。

`nameKeywords`（26 个）：

```
短剧 画 漫剧 AI 充电 红果 专属 动画 免费 剪辑 花絮 拍摄 经典 剧 真人 免 动漫 动 & 定档 首播 漫 ai 果 论剑大会
```

**规则（`getKeywordRule`）**：把第3列命中的**全部**关键词都拿去和第4列比对：

| 情况 | 结果 |
|---|---|
| 第3列有命中的词，且**命中的每一个词第4列都有** | `dual=true` → 疑似正确，**继续往下判定** |
| 第3列有命中的词，其中**任一个**第4列没有 | `hit=true` → **模式2**（理由里列出缺的那些词） |
| 第3列一个词都没命中 | `hit=false, dual=false` → 继续往下判定 |

> ⚠️ **"任一缺失即全错"比旧规则严**：关键词表里有重叠的单字，同一个剧名会命中多个词。
> 实测（用抽取出的真实函数跑）：`红果短剧` vs `红果短剧` → 命中 `[短剧,红果,剧,果]` 全都有 → **放行**；
> 但 `红果短剧` vs `红果` → 缺 `[短剧,剧]` → **全错**；`免费短剧` vs `免费` → 同样全错。
> 想让这类"只差几个字"的组合放行，就得精简词表里的单字（`剧/动/画/漫/免/果/&`）。

### ② 母本最低线（`lowScoreFloor`=90）→ 模式2

**母本最高分**（第5列 = 子样本单条分的最大值）**可读**且 `< 90` → 模式2，**不看子样本**。
这是 9.1.7 之后**唯一**保留的"不看子样本"硬规则。**90 分是底线**：即使子样本里 777/601 够多，也不救 —— 也就是说"码多"不能救一个最高分低于 90 的合集。面板可调，设为 0 即关闭。

### ③ 其余一切情况 → 展开核对

包括：相似/不相似、匹配分 >95 / ≤95 / **读不到**。此时并不直接下结论，而是**先展开**，再按第五节判据定模式1或模式2。

> 🧪 **预演模式（9.3.0）**：面板勾选「预演（只判定不点击）」后，上面整条判定链 + 日志上报照跑，但**不点任何按钮**（全剧审核 / 批量错误 / 查询刷新全部跳过），本轮跑完直接汇总。改判定规则后先用它空跑核对，确认无误再关掉正式跑；上报记录里会带 `dryRun: true`。

**相似度**（第3列 vs 第4列，归一化＝转小写 + 去标点空格，只留中英文数字）：

- 连续相同字数 ≥ `similarMinSubstr`(2) **或** 公共不同字数 ≥ `similarMinCommonChars`(3) → 相似；
- 任一列为空 → 记为不相似（理由写"无法比对"）；
- 结果只用于日志与 `expandKind` 标签，**不影响通过与否**。

**日志标签 `matchMode`（expandKind）**：

| 条件 | 标签 |
|---|---|
| 匹配分读不到 | `no-score` |
| 相似 且 匹配分 > 95 | `similar-high` |
| 相似 且 匹配分 ≤ 95 | `similar` |
| 不相似 且 匹配分 > 95 | `dissimilar-high` |
| 不相似 且 匹配分 ≤ 95 | `dissimilar` |

> ⚠️ 面板上的「匹配分阈值」（`parentScoreThreshold`=95）**目前只决定这里打 `-high` 还是不带**，对结果没有任何影响（见第十节疑点 1）。

## 五、展开核对判据（v9.3.0）

### 先剔除"还没刷新出来"的行（v9.3.0）

子样本**得分（第8列）= 0 或读不到** → 判定为「这条还没刷新出来」，**整行不计入判定统计**（既不算有效行，也不算低分/高分/正确数据）。
日志与判定理由里会写明排除了多少条：

```
子样本统计：共 52 条 | 状态码 0×40, 777×12 | 777 12 条 / 601 0 条
  | 得分≥93 11 条 | 低分<80 1 条 | 正确数据 12 条 | 有效 12 条（40 条 0分/读不到未计入） | 已打594 0 条
```

> ⚠️ **594 进度仍按全部行算**（"等全部子样本变 594"不受剔除影响），判定码 777/601 也照全部行计数 —— 只有 **base(有效行) / 低分 / 高分 / 正确数据** 这四项排除 0 分行。

### 统计量（`getCodeStats`）

| 统计量 | 含义 |
|---|---|
| `total` | 展开后**渲染出的**子样本行数（含没刷新的） |
| `valid` | **有效行数** = `total − notReady`（9.3.0） |
| `notReady` | 得分 = 0 或读不到的条数（9.3.0） |
| `wrong` / `notWrong` | 状态码 = `594` 的条数 / 其余条数（按全部行） |
| `judgeCounts` | `{777: n, 601: m}` 各自条数（`judgeCodes` 可配） |
| `scoreHigh` | 有效行中得分 **≥ 93**（`highScoreThreshold`）的条数 |
| `scoreLow` | 有效行中 **0 < 得分 < 80**（`lowScoreThreshold`）的条数（9.3.0） |
| `correct` | **正确数据条数** = 判定码 777/601 或 得分 ≥ 93 的**行数**（同一行只算一次）（9.3.0） |
| `scoreKnown` | 能读到得分的条数（排查列错用） |
| `unjudged` | 状态码为空或 `0` 的条数 |

### 判据（书写顺序 = 优先级）

1. **低分占优 → 模式2**（9.3.0 新增）：`scoreLow > correct` → 全错，**优先于下面"高分够多就通过"**；
2. **高分数据够多 → 模式1**：`scoreHigh ≥ highScoreMinCount`（**默认 4**，不分合集大小）；**或**
3. **前人已判定 → 模式1**：存在 `judgeCode` 条数 ≥ 门槛 —— **有效行 ≤ 30 条（`smallCollectionMaxRows`）→ ≥2**；**> 30 条 → ≥4**。777 与 601 **各自独立计数**，任一达标即可；
4. 以上都不满足 → **模式2（全错）**。

判定理由会拼成一行中文，例如：

```
两列不相似、匹配分 99（dissimilar-high），展开后：777 29 条 / 601 0 条 / 得分≥93 40 条
  / 低分<80 2 条 / 正确数据 41 条 / 有效 75 条 → 得分≥93 的条数 40 ≥ 4 → 判该合集正确
两列相似、匹配分 96（similar），展开后：777 2 条 / 601 0 条 / 得分≥93 3 条
  / 低分<80 9 条 / 正确数据 5 条 / 有效 20 条 → 低分(<80) 9 条 > 正确数据 5 条 → 全错
```

> 📌 **暂未实现的规则**：需求里提过"正确数据 > 有效行的一半 → 不考虑关键词和别的（多数即正确）"，本轮按你的要求**先跳过不做**（9.3.0/9.4.0 均未实现），需要时再补。

## 六、两种模式的执行动作

### 模式1：判正确

```
展开合集（等子样本渲染 + 等转圈结束）
 → 点击「全剧审核」+ 确认弹窗          （失败重试 2 次，间隔 2s；
                                        若仍失败且提供了 expandFn 才展开后重试）
 → 等「全剧审核」触发的转圈结束         （loadingWaitMax：普通 90s / 慢 150s）
 → 等合集被移走                        （fullReviewWaitMax：90s / 150s）
      完成标志（三者之一）：该行消失 / 该行状态含「已审核」/ 第2列 id 已变化
      等待中度过的第 30s、60s 各重试点击一次「全剧审核」（仅当页面已静止）
 → 超时未移走 → problem（收起 + 永久跳过）
```

> 模式1 **不勾选任何子样本、不点「批量错误」**，直接点「全剧审核」。这正是被删掉的 10.0 想改的点（10.0 要求"正确的也要先勾选再提交"）。

### 模式2：判全错

```
展开合集（同一入口）
 → 等转圈结束
 → 全选全部子样本        表头全选框优先；点完统计勾选数，若为 0 → 逐行勾选兜底
                        勾选到 0 条 → problem（判该合集有问题）
 → 等转圈结束
 → 点击「批量错误」+ 确认  （失败自动重试 3 次，间隔 3s；按钮消失视为已提交）
 → 等全部子样本 = 594 且无转圈
                        每 500ms 采样；等待期间第 30s / 60s 各重试点一次「批量错误」（页面静止才重试）
                        超时（90s / 150s）→ problem
 → 落库缓冲 1000ms（慢合集 3000ms）
 → 点击页面「查 询」刷新列表   （定位：非面板、非弹窗、未禁用、可见、文本去空格 == '查询' 的按钮）
 → 等转圈结束 → 等该合集移走
                        超时**不算失败**：既然已全判 594，按完成处理继续下一行
```

> 模式2 **一定**会执行「全选 + 批量错误」，即使子样本里已经没有 `0`（例如全是 777/601 或已经全 594）——没有"跳过判错"的路径。

## 七、等待 / 重试 / 兜底机制

| 机制 | 实现要点 |
|---|---|
| **转圈闸门** `isLoading()` | 命中任一即视为"处理中"：`button.ant-btn-loading` / `.ant-spin-dot-spin` / 各容器内 `.ant-spin-spinning` / 页面上任何非面板内的 `.ant-spin-spinning` |
| **加载完成** `waitLoadingDone()` | 必须**连续 800ms**（`loadingCalmMs`）无转圈才算完成；超时→本次不点击（安全放弃）；`strictLoading=false` 时直接返回 true |
| **确认弹窗** | 先找 `.ant-popconfirm` 里的"确定/确认/删除"（排除"取消"），再找 `.ant-modal` 内 `button.ant-btn-primary`；点击用 `mousedown + click + mouseup`（适配 React 合成事件）；点前还会等一次转圈结束（20s） |
| **等待期重试** | `retryAtSec=[30,60]`：到点若**页面已静止但状态未变**才重试点击同一按钮；还在转圈则跳过重试继续等。含首次，每个按钮最多 3 次 |
| **永久跳过** | 任一环节 problem → 收起该合集、记入 `skipList`、加入 `skipIds`，**换下一行继续**（不整脚本停止）；跳过数达 `maxSkipCount`(20) → 停止并提示人工 |
| **防重复处理** | 成功处理过的合集 id 记入 `doneIds`——「查 询」刷新后列表里可能还在，靠它避免重复处理 |
| **慢处理** | 集数 > 300（面板可调）→ 展开 30s / 加载 150s / 判错 150s / 全剧 150s / 落库 3s / 确认弹窗就绪 40s。**9.1.9 起该档位覆盖全部转圈闸门**（展开后加载、点击按钮前、点击查询前、勾选子样本前/后、确认就绪）；此前这五处固定用普通档，「慢处理」只生效一半 |
| **结构自检** | 启动 1.5s 后在控制台打印前两行的 id / 短剧名 / 原短剧名 / 匹配分 / 集数 / 状态 + 相似判定结果 |

## 八、面板参数（改动即时生效，仅当次运行内存态）

| 面板项 | CONFIG | 默认 | 作用 |
|---|---|:---:|---|
| 起始行号 | `startRow` | 1 | **每轮扫描的起点**（9.2.0 起固定从这一行往下扫，不再是移动游标） |
| 母本最高分 | `parentScoreThreshold` | 95 | **仅日志标签**（`-high`），不影响结果 |

| 高分/低分阈值 | `highScoreThreshold` / `lowScoreThreshold` | 93 / 80 | 仅源码可调：**单条分（子样本第8列）** ≥93 = 高分数据；(0,80) = 低分数据（9.3.0） |
| 预演（只判定不点击） | `dryRun` | 关 | 9.3.0：勾选后判定与上报照跑、不点任何按钮，用于验证规则 |

| 严格等待加载完成 | `strictLoading` | 开 | 转圈闸门总开关 |
| 上报判定日志 | `reportEnabled` | 开 | POST `/judge_log` |

## 十、已知疑点 / 风险清单（供下一步改需求时取舍；~~删除线~~ + ✅ = 9.1.9 / 9.2.0 已修）

1. **`parentScoreThreshold` 已是"僵尸参数"**：9.1.7 取消"相似且 >95 直接通过"后，它只剩下决定日志标签 `-high` 的作用；面板上仍写「分以上=有正确数据」，容易误导。
2. ~~上报 `version` 硬编码 `9.1.5`~~ → **✅ 9.1.9 已修**：`buildJudgeEntry` 的 `version` 改为跟随脚本版本（现为 `9.1.9`），日志可区分版本。
3. **小合集分档依赖"渲染出的行数"**：`total` 是展开后当前渲染的子样本行数。若页面子表**分页**（或虚拟滚动只渲染一部分），`total` 可能小于真实条数 → 大合集被误判为小合集（门槛 4→2，更容易通过）；`scoreHigh`/`judgeCounts` 同样只统计了渲染出来的部分。**9.4.3 起会在检测到子表分页器时打印预警**（只提示，不改流程）。
4. ~~**`waitReviewCompleted` 用 `rows[state.workIndex]` 判定完成**：索引位移可能提前判定完成~~ → **✅ 9.4.3 已修**：改为"按合集 id 是否还在列表里 + 该行是否已变「已审核」"判断，不再依赖下标。
5. **模式1 不勾选**：判正确的合集只点「全剧审核」就提交，不做任何勾选动作（10.0 就是为这件事而起，现已删除）。
6. **高分判据不参与分档**：只有 777/601 门槛分大小合集，`scoreHigh ≥ 4` 是硬性统一值，且 `highScoreThreshold`(95) 与 `parentScoreThreshold`(95) 是两个独立常量（前者不可面板调）。
7. **重复判错的幂等性**：模式2 对已经全 594 的合集仍会"全选 + 批量错误"，靠流程幂等收场；如遇到 594 行不能被再次勾选/提交，会落到 problem 被永久跳过。
8. ~~回绕查找的相邻性~~ → **✅ 9.2.0 已随扫描方式取消**：不再有"回绕"这一步（每轮从起始行往下扫），`noScoreStreak` 的相邻判断因此只会往回跳时重置；仍需注意"列表在刷新途中"时这类计数可能被误打断。
13. **"已审核"作边界依赖列表顺序**：9.2.0 假定已审核的合集连续沉在下面（今天的日志也印证了 id 递减的顺序）。若某次刷新把"未审核行"排到"已审核行"之后，脚本**仍会继续全表扫描**（实现上是全扫而非遇到边界即停），所以不会漏审；但若这种混排是常态，`boundary` 的日志提示会失真。
9. **相似度两列都空 → 判"不相似"**：日志里写"无法比对"，但结果等价于不相似（9.1.7 后不再有实际影响）。
10. **确认弹窗等待上限 8s**：极端卡顿时可能点不到确认 → 走重试/跳过；`strictLoading` 关闭时整体更容易在"未加载完"就继续。
11. ~~注释与实现漂移~~ → **✅ 9.1.9 已修**：`matchMode` 注释已改为实际取值（`similar-high`/`similar`/`dissimilar-high`/`dissimilar`/`no-score`），上报 `version` 与脚本 `@description`（原文案仍在描述 9.1.0 的旧矩阵规则）也已更新。
12. ~~「慢处理」只接了 7 处~~ → **✅ 9.1.9 已修**：展开后加载、点击按钮前、点击查询前、勾选子样本前后、确认弹窗就绪全部纳入慢处理分档（详见第七节）。
